# container-wt Architecture

This document explains what `container-wt` installs and why it is structured this way.

## Purpose

`container-wt` is a plain Docker Compose template for development inside containers from git worktrees.

It avoids devcontainer-specific tooling. The installed project should remain understandable as:

- Docker Compose files
- Dockerfiles
- generated `.env` files
- small shell scripts

The core technical problem it solves is git metadata resolution inside containers.

## Git Worktree Problem

A normal git repository has a `.git` directory. When the repository is mounted into a container, git usually works.

A git worktree has a `.git` file instead:

```text
gitdir: /Users/you/project/.git/worktrees/feature-x
```

That path is an absolute host path. If the container cannot see the same path, git commands inside the container fail.

`container-wt` fixes this by mounting the git common directory at the same absolute path inside the container:

```yaml
volumes:
  - ${LOCAL_WORKSPACE_FOLDER}:/workspaces/${WORKTREE_NAME}:cached
  - ${GIT_COMMON_DIR}:${GIT_COMMON_DIR}:cached
```

The `.git` file is not rewritten. No symlink or container startup mutation is required.

## Install Modes

`container-wt` has two modes.

### Simple Mode

Simple mode is for CLI-first projects:

- command-line tools
- tests
- agents
- scripts
- projects that do not normally expose web ports

Simple mode does not install Traefik and does not map ports by default.

### Web Mode

Web mode is for browser-based development.

It installs Traefik as shared infrastructure and exposes one stable localhost URL:

```text
http://localhost:9876
```

That URL routes to whichever worktree app container is selected with:

```bash
.container/route.sh
```

Web mode intentionally uses active route selection instead of automatic per-branch subdomains. This is more reliable in remote development environments, SSH forwarding, browser preview URLs, and other contexts where wildcard localhost or dynamic hostnames are fragile.

## Installed Directory

Both modes use `.container/`:

```text
.container/
  Dockerfile.example
  Dockerfile
  docker-compose.yml
  init.sh
  .env
  .env.app.example
  .env.app
  hooks/
    on-create.sh
    on-delete.sh
```

Generated or local-only files are gitignored:

```text
.container/Dockerfile
.container/.env
.container/.env.app
.container/traefik/dynamic.yml
.worktreeinclude.local
```

## Dockerfile Model

The tracked file is:

```text
.container/Dockerfile.example
```

The local file Docker builds is:

```text
.container/Dockerfile
```

`init.sh` creates `.container/Dockerfile` from the example only if it is missing.

There is no base/local Dockerfile layering. If a project or developer needs tools, edit `.container/Dockerfile`.

## Environment Files

`.container/.env` is generated by `.container/init.sh`.

It contains machine-specific and worktree-specific Docker Compose values:

```env
COMPOSE_FILE=docker-compose.yml
PROJECT_NAME=...
WORKTREE_NAME=...
BRANCH_NAME=...
GIT_COMMON_DIR=...
LOCAL_WORKSPACE_FOLDER=...
```

Web mode also includes:

```env
NETWORK_NAME=...
APP_PORT=3000
```

`.container/.env.app.example` is tracked.

`.container/.env.app` is copied from the example only if missing and is then user-owned. It is for app runtime values such as API keys or database URLs.

`container-wt` does not use `envsubst`. App runtime env is not generated from a template.

## Web Infra

Web mode installs:

```text
docker-compose.infra.yml
.container/route.sh
```

`docker-compose.infra.yml` contains Traefik and optional commented examples for shared services.

Infra services use the `infra` profile:

```yaml
profiles:
  - infra
```

If root `.env` does not exist, web init creates:

```env
COMPOSE_FILE=docker-compose.infra.yml
COMPOSE_PROFILES=infra
PROJECT_NAME=myapp
NETWORK_NAME=devnet-myapp
TRAEFIK_HOST=127.0.0.1
TRAEFIK_PORT=9876
```

If root `.env` already exists, it is not overwritten. Existing Compose behavior must be preserved manually.

## Routing

`route.sh` is web-mode only.

It writes Traefik dynamic config to the main repo directory:

```text
${MAIN_REPO_DIR}/.container/traefik/dynamic.yml
```

It resolves the main repo from git metadata, so it can be run from any worktree.

Supported commands:

```bash
.container/route.sh
.container/route.sh <worktree-name>
.container/route.sh <worktree-name> <app-port>
```

No argument means route the current worktree.

The route is a catch-all path route:

```yaml
rule: "PathPrefix(`/`)"
```

This avoids depending on a specific Host header.

`route.sh` requires the target app container to already be running. It does not build or start containers.

## Hooks

Hooks are installed but not wired automatically.

`on-create.sh`:

- copies files listed in `.worktreeinclude`
- copies files listed in `.worktreeinclude.local`
- runs `.container/init.sh`

`on-delete.sh`:

- removes `app-${PROJECT_NAME}-${WORKTREE_NAME}`
- runs `git worktree prune`
- does not modify Traefik routing

## Name Generation

`PROJECT_NAME` defaults to the main repo directory, derived from `git rev-parse --git-common-dir`.

Generated names use hyphens:

```text
feature/login -> feature-login
my_app -> my-app
```

## Safety Rules

`container-wt` should not overwrite user-owned local files:

- `.container/Dockerfile`
- `.container/.env.app`
- root `.env`
- existing project Compose files

Installer output includes skipped/unmodified files so a setup assistant can inspect them and propose minimal changes.
